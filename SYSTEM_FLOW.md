# M.A.S.H. System Flow Documentation

This document outlines the complete system flow for the M.A.S.H. (Mushroom Automation with Smart Hydro-environment) project, detailing the architecture, data communication, and user journeys for each component of the ecosystem.

## 1. High-Level Conceptual Framework (Input-Process-Output)

The system operates on a continuous feedback loop, transforming real-time data into automated actions and business intelligence.

-   **Input:**
    -   **Environmental Data:** Real-time sensor readings from the growing chamber, including temperature (±0.5°C accuracy), humidity (±2% accuracy), CO₂ levels, and device battery status.
    -   **User Data:** Sales, order, and inventory data generated by growers and consumers on the e-commerce platform.

-   **Process:**
    -   **AI & ML Analysis:** The NestJS backend uses machine learning algorithms to analyze sensor data, dynamically optimizing environmental parameters and predicting contamination or stress conditions.
    -   **E-commerce Management:** The backend processes sales orders, manages product listings and inventory, and coordinates logistics.
    -   **Actuator Control:** The system translates AI-driven decisions into commands for the hardware.

-   **Output:**
    -   **Automated Environmental Control:** Actuator commands are sent to humidifiers, fans, and ventilation systems to maintain the optimal growing environment.
    -   **Real-time Alerts & Dashboards:** Growers receive instant notifications and can view performance dashboards on the mobile app.
    -   **E-commerce Analytics:** The system generates sales reports, order tracking updates, and business analytics for growers and administrators.

## 2. System Architecture

The M.A.S.H. system is built on a two-layer architecture that separates the physical hardware from the software intelligence.

### 2.1. IoT Layer (Hardware)

This layer consists of the physical components responsible for cultivation and environmental control.

1.  **IoT-Enabled Growing Chamber:**
    -   **Controller:** A **Raspberry Pi Zero 2W** acts as the central hub, collecting data and executing commands.
    -   **Sensors:** A sensor module captures **CO₂, temperature, and humidity**.
    -   **Actuators:** Includes a **humidifier, blower fan, HEPA-filtered ventilation fans, and an exhaust unit** to regulate the microclimate.
    -   **Display:** A 20x4 I²C LCD screen provides on-site, real-time status updates.

2.  **Laminar Flow Hood:**
    -   A separate, standalone unit used for sterilizing fruiting bags and spawn before they are placed in the growing chamber. It is not connected to the IoT system.

### 2.2. Software Layer (AI, Backend, and Frontend)

This layer provides the intelligence, user interfaces, and data management for the entire system.

-   **Backend (NestJS):**
    -   The central API that handles data ingestion from the IoT devices.
    -   Runs the **AI and machine learning algorithms** for environmental analysis and prediction.
    -   Manages all business logic for the e-commerce platform.

-   **Databases:**
    -   **PostgreSQL:** The primary database for long-term storage of structured data (users, products, orders, transactions).
    -   **Firebase Realtime Database:** Used for live, low-latency communication of sensor data and real-time notifications.
    -   **SQLite:** Implemented on the Raspberry Pi for local caching, allowing the system to operate offline and sync data once connectivity is restored.

-   **Frontend Applications:**
    -   **Grower Mobile App (Flutter):** A cross-platform application that provides growers with a real-time dashboard, remote control of actuators, and AI-driven alerts.
    -   **Admin Web Dashboard (Next.js):** A comprehensive portal for system administrators to manage users, roles, system configurations, and view overall analytics.
    -   **E-commerce Platform (Next.js):** The public-facing marketplace that connects growers with consumers, featuring product listings, order management, and payment processing.

## 3. End-to-End Communication & Data Flow

The following steps describe the journey of data from the sensor to the end-user.

1.  **Data Collection:** The sensors inside the growing chamber continuously monitor the environment.
2.  **Local Processing:** The Raspberry Pi collects the raw sensor data.
3.  **Data Transmission:** The data is transmitted via Wi-Fi to the NestJS backend and Firebase Realtime Database. If offline, data is cached locally in SQLite.
4.  **AI Analysis:** The backend's AI module processes the incoming data to detect deviations from optimal conditions or predict future needs (e.g., an impending need for more humidity).
5.  **Automated Response:** Based on the analysis, the backend sends commands back to the Raspberry Pi, which triggers the appropriate actuators (e.g., activates the humidifier).
6.  **User Notification:** Simultaneously, updated conditions and alerts are pushed to the grower's Flutter mobile app and displayed on the chamber's LCD module.
7.  **E-commerce Sync:** Harvest data and inventory levels can be updated on the e-commerce platform, synchronizing the farm's physical output with the digital marketplace.

## 4. User Process Flows

This section details the primary user journeys within the M.A.S.H. software ecosystem.

### 4.1. Authentication Flow (Login & Sign Up)

-   **Sign Up:**
    1.  User initiates sign-up via standard email/password or a Single Sign-On (SSO) provider (e.g., Google).
    2.  The system requires **OTP verification** via email or SMS to validate the user's identity.
    3.  Upon successful verification, the user account is created, and the user is logged in.
-   **Login:**
    1.  User logs in using credentials or SSO.
    2.  A "Forgot Password" flow is available, which requires identity verification and an OTP to reset the password.

### 4.2. Consumer User Flow

1.  **Browse & Discover:** A consumer visits the M.A.S.H. Market website, browsing products via search, categories, or recommendations.
2.  **Add to Cart:** The consumer adds desired mushroom products to their shopping cart.
3.  **Checkout:** The consumer proceeds to checkout, where they are prompted to log in or sign up.
4.  **Order Placement:** The consumer confirms their order and completes the payment.
5.  **Order Confirmation:** The order is confirmed, and the consumer can track its status.
6.  **Item Received:** Upon receiving the product, the consumer marks the order as complete and has the option to rate the product. If the item is incorrect, they can contact the seller.

### 4.3. Seller (Grower) User Flow

1.  **Dashboard:** After logging in, the seller is directed to their main dashboard, which provides an overview of their operations.
2.  **Product Management:**
    -   **View Catalog:** See all active product listings.
    -   **Add Product:** Create a new listing with details like price, description, and images.
    -   **Edit/Disable Product:** Update or temporarily remove existing listings.
3.  **Order Management:**
    -   **View Orders:** See a list of all orders, categorized by status (Pending, Completed, Returned).
    -   **Fulfill Order:** Process a new order, prepare it for shipping, and contact the customer if needed.
4.  **Analytics:** Access sales reports and performance metrics to track business growth.

### 4.4. Administrator User Flow

1.  **System Overview Dashboard:** View system-wide metrics, active devices, total users, and sales analytics.
2.  **User & Role Management:** Manage user accounts, assign roles (Super Admin, Admin, Grower, Buyer), and configure permissions via RBAC.
3.  **Device Registration:** Register new IoT devices (Raspberry Pi controllers) and assign them to grower accounts.
4.  **Logistics Management:** Monitor handover centers, manage pickups, process returns/refunds.
5.  **System Configuration:** Configure global settings, alert thresholds, rate limits, and cache policies.

**Step-by-Step Flow:**

1.  **Data Collection (Every 10 seconds):**
    -   Sensors capture environmental readings: Temperature (±0.5°C), Humidity (±2%), CO₂ levels (ppm).
    -   Raspberry Pi polls sensors via GPIO pins using Python scripts.

2.  **Local Processing:**
    -   Raspberry Pi validates sensor data (range checks, outlier detection).
    -   Data is formatted into JSON payload with timestamp and device ID.

3.  **Transmission to Cloud:**
    -   Data is sent simultaneously to:
        -   **Firebase Realtime Database:** For instant mobile app updates (WebSocket connection).
        -   **NestJS Backend:** For persistent storage, AI analysis, and historical tracking.

4.  **AI Analysis (NestJS Backend):**
    -   Machine learning model evaluates current conditions against optimal thresholds:
        -   **Temperature:** 20-28°C (optimal: 24-26°C)
        -   **Humidity:** 80-95% (optimal: 85-90%)
        -   **CO₂:** 800-1200 ppm (optimal: 1000 ppm)
    -   AI predicts contamination risk based on pattern analysis.
    -   If conditions deviate, AI generates actuator commands.

5.  **Actuator Control:**
    -   Backend sends commands back to Raspberry Pi via MQTT protocol:
        -   `HUMIDIFIER_ON`: Activate humidifier if humidity < 80%
        -   `FAN_ON`: Turn on exhaust fan if CO₂ > 1200 ppm or temp > 28°C
        -   `BLOWER_ON`: Increase air circulation
    -   Raspberry Pi executes commands via F5305S MOSFET board.

6.  **User Notification:**
    -   Mobile app receives real-time updates via Firebase.
    -   LCD display shows current readings and actuator status.
    -   Push notifications sent for critical alerts (e.g., high contamination risk).

**Offline Behavior:**

1.  **Data Buffering:** Sensor readings are stored in local SQLite database on the Raspberry Pi.
2.  **Local Actuator Control:** Basic automated responses continue based on pre-configured thresholds stored locally.
3.  **LCD Operation:** On-site display continues to show real-time data.
4.  **Sync on Reconnect:** When internet is restored:
    -   Raspberry Pi detects connectivity.
    -   Batch uploads all cached data to NestJS backend.
    -   Backend processes historical data and updates analytics.
    -   Mobile app receives notification: "Offline data synchronized."

## 6. AI-Driven Environmental Optimization

The M.A.S.H. system uses machine learning to provide predictive and adaptive environmental control.

### 6.1. AI Model Architecture

-   **Input Features:**
    -   Current Temperature, Humidity, CO₂
    -   Historical trends (last 24 hours)
    -   Time of day, mushroom growth stage
    -   External weather data (optional)

-   **ML Algorithm:** Trained regression model (likely Random Forest or Neural Network) that predicts:
    -   Optimal actuator settings for next time window
    -   Contamination risk probability
    -   Expected yield based on current conditions

-   **Training Data:** Historical data from successful mushroom cultivation cycles, including:
    -   Sensor readings every 10 seconds
    -   Harvest yield outcomes
    -   Contamination incidents (labeled dataset)

### 6.3. Contamination Detection

The AI model uses pattern recognition to detect early signs of contamination:

-   **Indicators:**
    -   Sudden humidity spikes
    -   Prolonged high CO₂ levels
    -   Temperature instability
    -   Sensor reading anomalies

-   **Alert Levels:**
    -   **Low (0-30%):** Informational notification
    -   **Medium (31-60%):** Warning with recommended actions
    -   **High (61-100%):** Critical alert, immediate intervention required

-   **Automated Response:**
    -   Increase ventilation
    -   Adjust humidity levels
    -   Notify grower via push notification and SMS

## 8. Database Synchronization Strategy

### 8.1. Three-Tier Data Storage

1.  **PostgreSQL (Primary Database):**
    -   Long-term storage of all structured data
    -   User accounts, roles, permissions
    -   Product catalog, orders, transactions
    -   Historical sensor data (aggregated)
    -   Sales analytics

2.  **Firebase Realtime Database:**
    -   Live sensor readings (last 1 hour)
    -   Real-time actuator status
    -   Active user sessions
    -   Push notification queue
    -   WebSocket connections for mobile app

3.  **SQLite (Edge/Offline Storage):**
    -   Installed on Raspberry Pi
    -   Buffers sensor data during internet outages
    -   Stores local actuator control logic
    -   Syncs to cloud when online

### 8.2. Data Flow Between Databases

```
  Raspberry Pi (SQLite)
         │
         │ Every 10s (if online)
         ▼
  Firebase Realtime DB ◄─────► Flutter Mobile App
         │                      (Live updates)
         │ Every 10s
         ▼
  NestJS Backend
         │
         │ Batch write (every 5min)
         ▼
  PostgreSQL
  (Historical archive)
```

### 8.3. Conflict Resolution

-   **Last-Write-Wins:** For sensor data, the latest timestamp is authoritative.
-   **User Edits:** Product/order updates use optimistic locking with version numbers.
-   **Offline Conflicts:** When Raspberry Pi reconnects, any conflicts are flagged for manual review.

## 9. Security & Authentication Flow

### 9.1. User Authentication (JWT + OTP)

```
1. User Login Request
   └─> POST /api/v1/auth/login
       - Email + Password OR SSO (Google)

2. Backend Validation
   └─> NestJS verifies credentials
       - Bcrypt password hash comparison
       - Or SSO token validation

3. OTP Verification (First login or suspicious activity)
   └─> Send OTP via:
       - Email (using SendGrid/Nodemailer)
       - SMS (using Twilio)
   └─> User enters OTP code
   └─> Backend validates OTP (expires in 10 minutes)

4. JWT Token Issued
   └─> Response includes:
       - Access Token (expires in 1 day)
       - Refresh Token (expires in 30 days)
   └─> Stored in:
       - Mobile app: Secure storage (flutter_secure_storage)
       - Web: HTTP-only cookie

5. Authenticated Requests
   └─> Every API call includes:
       - Authorization: Bearer <access_token>
   └─> NestJS verifies JWT signature and expiration
```

### 9.2. Role-Based Access Control (RBAC)

The system uses a granular permissions model:

-   **Super Admin:** Full system access, user management, system configuration.
-   **Admin:** Manage users, view all analytics, moderate content.
-   **Grower:** Access own IoT devices, manage own products, view own sales.
-   **Buyer:** Browse products, place orders, track shipments.
-   **Guest:** Browse products only (no purchase without login).

**Permission Examples:**
-   `devices:read:own` - Grower can view their own devices
-   `devices:read:all` - Admin can view all devices
-   `orders:create` - Buyer can place orders
-   `users:manage` - Admin can create/edit/delete users

## 10. Performance Optimization & Caching

### 10.1. Redis Caching Strategy

The system uses Redis (Upstash) for aggressive caching to achieve 85-90% hit rate:

-   **Product Listings:** Cached for 10 minutes (`CACHE_TTL_PRODUCTS=600`)
-   **Categories:** Cached for 30 minutes (rarely change)
-   **User Sessions:** Cached for entire session duration
-   **Analytics Queries:** Cached for 30 minutes (expensive to compute)
-   **Sensor Data (Latest):** Cached for 1 minute (frequent updates)

**Cache Invalidation:**
-   On product update/delete: Clear `product:{id}` and `products:*`
-   On order placement: Clear `inventory:*`
-   On user role change: Clear `user:{id}:permissions`

### 10.2. Rate Limiting

Role-based rate limiting prevents abuse:

-   **Super Admin:** 10,000 requests/min
-   **Admin:** 1,000 requests/min
-   **Grower:** 200 requests/min
-   **Buyer:** 150 requests/min
-   **Guest:** 20 requests/min

**Endpoint-Specific Limits:**
-   Analytics endpoints: 10 requests/min (expensive queries)
-   Standard CRUD: 100 requests/min
-   Lightweight reads: 1,000 requests/min

## 11. Monitoring & Observability

### 11.1. Metrics Collection (Prometheus)

The system exposes `/metrics` endpoint with 60+ custom metrics:

-   **HTTP Metrics:** Request count, duration, status codes by endpoint
-   **Database Metrics:** Query count, duration, connection pool usage
-   **Cache Metrics:** Hit rate, miss rate, eviction count
-   **Business Metrics:** Orders per hour, revenue, active devices
-   **IoT Metrics:** Sensor reading frequency, actuator commands, offline incidents

### 11.2. Distributed Tracing (OpenTelemetry + Jaeger)

Every request generates a trace spanning:
1.  HTTP request received
2.  Database query executed
3.  Cache lookup
4.  External API call (payment gateway)
5.  IoT device command sent
6.  Response returned

Traces include:
-   Request ID (correlation across services)
-   User ID (for debugging user-specific issues)
-   Performance bottlenecks (slow queries highlighted)

### 11.3. Alerting (Prometheus Alertmanager)

Alerts triggered for:
-   **Critical:** Database down, API error rate > 5%, IoT device offline > 30 min
-   **Warning:** High memory usage (>80%), slow queries (>1s), cache hit rate < 70%
-   **Info:** New device registered, large order placed (>₱10,000)

Alerts sent via:
-   Email (SMTP: Gmail)
-   Slack (webhook)
-   SMS (Twilio, for critical only)
